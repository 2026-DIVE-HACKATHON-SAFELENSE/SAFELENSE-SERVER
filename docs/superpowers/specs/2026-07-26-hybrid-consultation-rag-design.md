# 실제 비식별 상담 데이터 하이브리드 RAG 설계

## 목표

공공 데이터와 등기부에서 찾은 계약 위험요소를 Rule Engine으로 구조화한 뒤, 실제 비식별 상담 사례 938건에서 조건과 맥락이 유사한 사례를 검색한다. 검색 결과는 OpenAI 리포트 생성 입력으로만 사용하고, 최종 리포트에는 사용자가 이해할 수 있는 유사 사례 요약과 행동 가이드를 근거 ID와 함께 남긴다.

## 데이터 출처와 표시

제공된 `비식별_임대차상담데이터.xlsx`의 상담 데이터는 938건이며 다음 16개 열을 가진다.

- 식별·시점은 일련번호, 자료군, 상담월이다.
- 계약 조건은 지역, 보증금구간, 계약상태, 주택유형, 선순위권리, 보증보험이다.
- 사건 결과는 분쟁유형과 진행단계다.
- 비식별 텍스트는 상황요약, 담당자의견, 특이사항, 상담변호사 코드다.

정의서상 출처는 전세세입자모임·임차in의 변호사 심층상담 사례다. HUG 제공 데이터가 아니므로 코드와 리포트에서 `HUG`로 표시하지 않는다. 이번 데이터의 출처 코드는 `DIVE_2026_COUNSELING`으로 고정하고, 향후 실제 HUG 데이터가 추가되면 별도 출처 코드와 데이터셋 버전을 사용한다.

원본 엑셀은 저장소에 커밋하지 않는다. 서비스 응답에도 원문 상황요약, 담당자의견, 상담변호사 코드를 그대로 노출하지 않는다.

## 저장 모델

Flyway 마이그레이션으로 `consultation_cases`와 `analysis_case_matches`를 추가한다.

`consultation_cases`는 다음 정보를 보관한다.

- 내부 ID와 유일한 `source_case_id`.
- `source`, `dataset_version`, `consultation_month`.
- 시도·시군구, 보증금구간, 계약상태, 주택유형, 선순위권리, 보증보험.
- 분쟁유형, 진행단계.
- 상황요약, 담당자의견, 특이사항, 상담변호사 코드.
- 상황요약 검색용 임베딩 JSON, 임베딩 모델, 임베딩 생성 시각.
- 생성·수정 시각.

`analysis_case_matches`는 분석 실행 당시 선택한 사례를 불변 스냅샷으로 남긴다.

- `run_id`, `consultation_case_id`, 순위.
- 구조화 점수, 의미 유사도, 최종 점수.
- 리포트에 표시할 일반화된 사례 요약.

같은 분석 실행에서 같은 상담 사례를 두 번 저장하지 않으며, 순위도 중복되지 않게 한다.

## 일회성 적재

저장소에는 원본 데이터가 아니라 재실행 가능한 import 스크립트만 추가한다. 스크립트는 다음 순서로 동작한다.

1. 명령행 인자로 받은 XLSX의 `비식별_상담데이터` 시트를 읽는다.
2. 필수 헤더 16개와 행별 `일련번호`를 검증한다.
3. `source_case_id`를 `DIVE-2026-{일련번호}` 형식으로 만든다.
4. 상황요약이 있는 행은 기존 OpenAI 설정과 별도의 임베딩 모델 설정으로 벡터화한다.
5. `source_case_id` 기준으로 PostgreSQL에 upsert한다.
6. 전체 건수, 신규·갱신·실패 건수만 로그에 남기고 상담 원문은 로그에 쓰지 않는다.

일련번호가 같아도 데이터셋 버전이 바뀌면 명시적으로 갱신한다. 세 건의 빈 상황요약은 구조화 검색에는 포함하되 의미 점수는 계산하지 않는다. 임베딩 API 실패 행은 DB에 반영하지 않고 실패 목록만 별도 출력해 재실행할 수 있게 한다.

## 검색 입력

현재 `ConsultationCaseMatcher.match(evidence)`는 매물과 Rule Engine 결과를 받지 못하므로 다음 입력 객체로 교체한다.

`ConsultationSearchQuery`는 매물의 보증금구간과 주택유형, 주소에서 로컬 규칙으로 추출한 시도, 수집 근거에서 해석한 선순위권리와 보증보험, Rule Engine의 등급·위험 신호·권고사항을 가진다. 상세 주소, 시군구 이하 주소, 임대인명, 등기부 원문은 포함하지 않는다.

분석 워커 순서도 다음처럼 변경한다.

`수집 → 등기부 추출 → Rule Engine → 상담 사례 검색 → LLM 리포트`

## 하이브리드 검색

구조화 점수와 의미 점수를 함께 사용한다.

구조화 점수의 기본 가중치는 다음과 같다.

- 보증금구간 30.
- 주택유형 20.
- 선순위권리 25.
- 보증보험 15.
- 시도 10.

알 수 없는 입력은 불일치로 처리하지 않고 분모에서 제외한다. 계약상태, 분쟁유형, 진행단계는 계약 전 입력이 아니라 사례의 결과이므로 검색 조건에 넣지 않는다.

Rule Engine 결과와 사용 가능한 구조화 위험요소를 개인정보 없는 짧은 검색 문장으로 만들고 OpenAI 임베딩을 생성한다. 후보 사례의 상황요약 임베딩과 코사인 유사도를 계산한다.

최종 점수는 `구조화 점수 55% + 의미 점수 45%`로 계산한다. 상황요약이 없어 의미 점수를 계산할 수 없는 사례는 구조화 점수만 사용하고 장애로 처리하지 않는다. 938건 규모에서는 PostgreSQL 확장에 의존하지 않는다. 구조화 조건으로 최대 100건을 먼저 조회한 뒤 애플리케이션에서 코사인 유사도를 계산한다. 최종 점수 0.45 이상인 상위 3건만 사용한다.

향후 사례가 수만 건 이상으로 증가하면 검색 인터페이스는 유지하고 pgvector 기반 구현으로 교체한다.

## 리포트와 근거 검증

`MatchedCase`에는 사례 근거 ID, 출처, 분쟁유형, 진행단계, 구조화·의미·최종 점수, LLM 입력용 비식별 요약을 포함한다.

최종 리포트에는 `similarCases`를 추가한다. 각 항목은 다음 정보만 노출한다.

- `case-{id}` 형식의 근거 ID.
- 출처 코드.
- 유사도.
- 분쟁유형과 진행단계.
- 구조화 필드로 만든 일반화된 사례 설명.

원문 상황요약과 담당자의견은 검색과 LLM 해석에만 사용하고 API에 그대로 반환하지 않는다.

현재 근거 검증기는 `evidence-{id}`만 허용하므로 `case-{id}`도 허용한다. AI는 공공 데이터 근거와 상담 사례 근거를 함께 인용할 수 있지만, 상담 사례를 사용자의 법적 결론이나 사고 확률로 일반화할 수 없다. 기존 법률 단정과 근거 없는 숫자 차단 규칙은 유지한다.

## 데이터 모드

`AnalysisDataMode`에 `MIXED`를 추가한다.

- 공공·상담 데이터가 모두 데모이면 `DEMO`.
- 둘 중 하나만 실제 데이터이면 `MIXED`.
- 모든 분석 데이터가 실제 제공처에서 수집되면 `LIVE`.

현재 `DemoPropertyDataCollector`와 실제 상담 데이터를 함께 사용하므로 새 분석 실행은 `MIXED`다. `dataMode`는 검색 분기를 제어하지 않고 리포트의 데이터 구성 상태를 표시한다. 실제 검색 구현 선택은 주입된 수집기와 매처가 담당한다.

## 실패 처리

- 임베딩 질의가 실패하면 구조화 점수만으로 최대 3건을 반환하고 분석 실행을 `PARTIAL`로 표시한다.
- 상담 DB 조회가 실패하면 사례 없이 규칙 기반 리포트를 생성하고 `PARTIAL`로 표시한다.
- 조건과 임계값을 만족하는 사례가 없는 것은 장애가 아니며 빈 `similarCases`로 정상 처리한다.
- 상담 사례 원문, 임베딩 요청 본문, DB 접속 정보는 로그에 남기지 않는다.

## 테스트

- Flyway 계약 테스트로 두 테이블, 유일 제약과 외래 키를 검증한다.
- import 스크립트 테스트로 헤더 검증, 938건 upsert, 재실행 멱등성, 빈 요약 처리를 검증한다.
- 구조화 점수 테스트로 정확한 일치, 미상 필드 제외, 결과 필드가 검색 조건에 쓰이지 않음을 검증한다.
- 의미 점수와 최종 가중치 테스트는 고정 벡터를 사용해 외부 API 없이 검증한다.
- 매처 테스트로 임계값, 상위 3건, 임베딩 실패 시 구조화 검색 폴백을 검증한다.
- 워커 테스트로 Rule Engine 이후 검색 순서, 매치 스냅샷 저장, 장애 시 `PARTIAL`을 검증한다.
- 리포트 테스트로 `similarCases`, `case-{id}` 인용 허용, 원문 미노출을 검증한다.
- API 테스트로 `/status`와 리포트의 `dataMode=MIXED`를 검증한다.

## 제외 범위

- 실제 공공 데이터 제공처 연동.
- 등기부 OCR과 권리관계 정밀 추출.
- pgvector 도입.
- 상담 원문 조회 API와 관리자 업로드 API.
- 상담 사례를 이용한 사고 확률 예측이나 법률 결론 생성.
