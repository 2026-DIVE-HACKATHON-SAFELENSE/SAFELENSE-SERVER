# SSM Parameter Store와 PostgreSQL 배포 설계

## 목표

prod 프로필의 SAFELENSE 서버가 AWS Systems Manager Parameter Store의 `/safelense/prod/` SecureString 8개를 Spring 데이터소스 초기화 전에 읽고, Supabase PostgreSQL과 함께 EC2 systemd 서비스로 안전하게 실행되게 한다.

## SSM 런타임 설정

`SPRING_PROFILES_ACTIVE=prod`일 때만 `EnvironmentPostProcessor`가 AWS SDK v2 SSM 클라이언트로 다음 8개 이름을 `withDecryption=true`로 한 번에 읽는다.

- `/safelense/prod/DB_URL`
- `/safelense/prod/DB_USERNAME`
- `/safelense/prod/DB_PASSWORD`
- `/safelense/prod/KAKAO_REST_API_KEY`
- `/safelense/prod/KAKAO_CLIENT_SECRET`
- `/safelense/prod/JWT_SECRET`
- `/safelense/prod/JWT_ACCESS_TOKEN_TTL`
- `/safelense/prod/JWT_REFRESH_TOKEN_TTL`

로더는 각 경로의 마지막 요소를 기존 Spring 속성 키로 사용해 가장 높은 우선순위의 property source에 넣는다. 따라서 현재 `application.yml`의 `${DB_URL}` 같은 placeholder는 변경하지 않는다. prod에서 AWS 자격 증명, 리전, SSM 연결, 파라미터 누락 중 하나라도 실패하면 값은 로그에 남기지 않고 서버 시작을 중단한다. local을 포함한 prod 이외 프로필에서는 SSM을 호출하지 않아 기존 환경 변수와 `.env` 주입 방식이 유지된다.

AWS SDK는 EC2 인스턴스 프로필과 로컬 AWS profile을 포함하는 기본 자격 증명 체인을 사용한다. prod 대상 리전과 접두사는 각각 `ap-northeast-2`, `/safelense/prod/`로 고정한다.

## PostgreSQL 전환

MySQL JDBC와 Flyway MySQL 모듈을 PostgreSQL JDBC와 Flyway PostgreSQL 모듈로 교체한다. 기존 V1~V6 Flyway 마이그레이션은 아직 적용되지 않은 새 Supabase PostgreSQL 데이터베이스를 전제로 PostgreSQL SQL로 바꾼다.

- `AUTO_INCREMENT`는 `GENERATED BY DEFAULT AS IDENTITY`로 바꾼다.
- `DATETIME(6)`는 `TIMESTAMP(6) WITH TIME ZONE`으로 바꾼다.
- `updated_at ON UPDATE`는 공통 PL/pgSQL 트리거 함수와 테이블별 trigger로 보존한다.
- MySQL의 테이블 내부 `INDEX`는 별도 `CREATE INDEX` 문으로 바꾼다.
- `MEDIUMBLOB`과 JPA `@Lob` 매핑은 PostgreSQL `BYTEA`와 일반 `ByteArray` 매핑으로 바꾼다.

이미 MySQL에 적용된 Flyway 이력이나 데이터를 자동 이전하지 않는다. 그러한 데이터가 있다면 별도 데이터 이전 작업이 필요하다.

## GitHub Actions와 EC2 배포

`main` push에서 GitHub Actions는 OIDC로 `AWS_ROLE_TO_ASSUME`를 Assume한다. GitHub Variables는 `AWS_ROLE_TO_ASSUME`, `AWS_REGION`, `EC2_INSTANCE_ID`만 사용하며 DB·Kakao·JWT 값은 참조하지 않는다.

워크플로는 Java 24으로 JAR를 만든 뒤 `safelense-deploy-artifacts-380906049995-ap-northeast-2` 버킷의 `releases/<commit SHA>/`에 JAR와 systemd 유닛을 올린다. 이어 SSM `AWS-RunShellScript`가 EC2 `i-0b94d776a7652178f`에서 `/opt/safelense/safelense-server.jar`와 `/etc/systemd/system/safelense.service`를 갱신하고 서비스를 재시작한다.

EC2에는 Java 24, AWS CLI v2, systemd가 준비돼 있어야 한다. 인스턴스 역할은 SSM parameter path 읽기·복호화와 배포 버킷 읽기만 허용한다. GitHub OIDC 역할은 해당 버킷 쓰기와 지정 EC2에 대한 SSM Run Command 상태 조회만 허용한다. 저장소에는 두 정책과 `main` 브랜치로 한정한 OIDC trust policy를 제공하지만 AWS IAM 리소스는 생성하지 않는다.

## 검증

SSM 로더는 prod property source 생성, 누락 파라미터 거부, non-prod 미호출을 단위 테스트로 검증한다. PostgreSQL 마이그레이션 파일과 `BYTEA` 매핑을 계약 테스트로 검증한다. 워크플로와 IAM JSON은 민감한 값·장기 키·SSH 사용이 없는지 정적 검토한다. 실제 AWS SSM, Supabase, EC2 연결은 계정 자격 증명과 서버 준비 상태가 필요한 통합 검증으로 남긴다.
