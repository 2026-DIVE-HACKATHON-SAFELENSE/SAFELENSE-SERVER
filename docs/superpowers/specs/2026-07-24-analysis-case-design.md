# 분석 케이스·규칙 기반 위험 분석 API 설계

## 목표

로그인 사용자가 사진의 `계약 전`, `계약 중`, `계약 후` 흐름에 따라 분석 케이스를 만들고, 단계별 서류와 체크리스트를 선택적으로 입력한 뒤, 연습 데이터에서 정리한 규칙으로 계약 위험도를 확인할 수 있게 한다.

사진과 노션 명세가 다르면 사진을 우선한다. 이번 범위에서 실제 AI 모델이나 외부 공공·민간 API는 호출하지 않는다. 서버는 구조화된 주택 정보, 문서 업로드 여부, 체크리스트 답변을 버전이 있는 규칙으로 평가한다.

## 범위

- `GET /api/v1/analysis-templates/{stage}`로 단계별 서류 슬롯과 탭별 체크리스트를 조회한다.
- `POST /api/v1/analysis-cases`로 주택과 계약 단계에 대한 분석 케이스를 생성한다.
- `GET /api/v1/analysis-cases/{caseId}`로 서류·체크리스트 입력 상태와 분석 결과 요약을 조회한다.
- `POST /api/v1/analysis-cases/{caseId}/documents`로 PDF 또는 이미지를 한 서류 슬롯에 업로드한다.
- `DELETE /api/v1/analysis-cases/{caseId}/documents/{documentId}`로 분석 전 서류를 삭제한다.
- `PUT /api/v1/analysis-cases/{caseId}/checklist`로 현재 체크리스트 답변 전체를 교체한다.
- `POST /api/v1/analysis-cases/{caseId}/analyze`로 입력 스냅샷을 고정하고 위험 분석 결과를 생성한다.

분석 이력 목록, 별도 분석 결과 상세 API, PDF 리포트, OCR, 문서 내용 추출, 관리자용 템플릿 편집, 실제 AI 모델 호출은 제외한다.

## 사진 우선 화면 계약

계약 단계는 `BEFORE_CONTRACT`, `DURING_CONTRACT`, `AFTER_CONTRACT` 세 값으로 제한한다. 각 단계의 서류 화면은 6개 슬롯과 `uploadedCount/6` 진행률을 제공한다.

체크리스트는 평면 문항 목록이 아니라 사진 상단 탭을 표현하는 섹션 목록으로 반환한다. 각 섹션은 안정적인 `sectionKey`, 표시 문구, 순서, 문항 목록을 가진다. 문항은 안정적인 `itemKey`, 표시 문구, 순서와 답변 형식을 가진다. 초기 카탈로그의 문구와 순서는 사진 및 제공될 연습 데이터의 입력 필드를 기준으로 고정한다.

`다음 단계`는 프론트엔드 화면 이동이므로 별도 서버 API를 만들지 않는다. 서류나 답변이 없어도 다음 화면으로 이동하고 분석을 실행할 수 있다.

## 데이터 모델

### 분석 케이스

`analysis_cases`는 `id`, `user_id`, `property_id`, `stage`, `status`, `template_version`, 생성·수정 시각을 저장한다. 상태는 `DRAFT`, `ANALYZED`만 사용한다.

케이스 생성 시 주택이 인증 사용자 소유인지 검증한다. 한 사용자가 같은 주택과 단계에 여러 케이스를 만들 수 있으며, 각 분석 시도는 독립된 기록이 된다.

### 분석 문서

`analysis_documents`는 `id`, `case_id`, `document_type`, 원본 파일명, MIME 타입, 파일 크기, 파일 바이트, 생성·수정 시각을 저장한다. `(case_id, document_type)`은 유일하며, 같은 슬롯에 재업로드하면 기존 문서를 교체한다.

MVP에서는 별도 파일 저장 인프라를 도입하지 않고 MySQL `MEDIUMBLOB`에 저장한다. 허용 형식은 PDF, JPEG, PNG이며 파일당 최대 크기는 10MiB다. 파일 내용은 이번 분석 점수에 사용하지 않고, 해당 서류가 제출됐다는 사실만 입력 특징으로 사용한다.

### 체크리스트 답변

`analysis_checklist_answers`는 `case_id`, `item_key`, 답변 값과 수정 시각을 저장한다. `PUT` 요청은 케이스의 기존 답변을 요청의 전체 답변 집합으로 교체한다. 빈 배열과 일부 답변을 허용하며, 템플릿에 없는 `itemKey`와 중복된 `itemKey`는 거절한다.

### 분석 결과

`analysis_results`는 케이스당 한 건만 저장한다. `id`, `case_id`, `idempotency_key`, nullable `score`, `grade`, `confidence`, 규칙 버전, 입력 스냅샷, 위험 요인, 누락 입력, 권고사항, 생성 시각을 포함한다.

위험 요인, 누락 입력, 권고사항과 입력 스냅샷은 분석 시점의 응답을 그대로 재현할 수 있도록 JSON으로 저장한다.

## 규칙 기반 분석

연습 데이터 원본을 런타임에 검색하거나 가장 비슷한 사례를 선택하지 않는다. 검토된 연습 데이터에서 위험 조건, 가중치, 설명과 권고사항을 추출해 버전이 있는 규칙 카탈로그로 관리한다.

규칙이 평가할 수 있는 입력은 다음으로 제한한다.

- `HomeProperty`의 구조화된 필드.
- 단계별 문서 슬롯의 업로드 여부.
- 단계별 체크리스트 답변.

각 규칙은 `ruleCode`, 적용 단계, 입력 키, 비교 연산, 기대값, 점수 영향, 사용자 설명과 권고사항을 가진다. 일치한 규칙의 점수 영향을 합산하고 결과를 0부터 100까지로 제한한다.

- 0~29점은 `LOW`.
- 30~59점은 `CAUTION`.
- 60~100점은 `HIGH`.

누락 입력은 0점이나 안전한 응답으로 치환하지 않는다. 확인할 수 있는 위험·안전 근거가 하나도 없으면 `score`는 `null`, `grade`는 `UNKNOWN`이다.

`confidence`는 현재 단계의 전체 문서 슬롯과 체크리스트 문항 중 값이 있는 항목의 비율을 0부터 100까지의 정수로 반환한다. 모든 문서와 답변은 선택 사항이므로 `confidence`는 분석 허용 여부에 영향을 주지 않는다. 비어 있는 슬롯과 문항 키는 `missingInputs`에 반환한다.

규칙 버전을 분석 결과에 저장하므로 이후 규칙이 바뀌어도 과거 결과는 변하지 않는다.

## API 동작

### 템플릿 조회

`GET /api/v1/analysis-templates/{stage}`는 단계, 템플릿 버전, 서류 슬롯 6개, 체크리스트 섹션과 문항을 반환한다. 알 수 없는 단계는 `400 INVALID_STAGE`다.

### 케이스 생성

`POST /api/v1/analysis-cases`는 `stage`, `propertyId`를 받는다. 주택이 없거나 다른 사용자 소유면 정보 노출을 막기 위해 `404 PROPERTY_NOT_FOUND`를 반환한다. 성공 시 `201 Created`와 새 케이스를 반환한다.

### 케이스 조회

`GET /api/v1/analysis-cases/{caseId}`는 본인 케이스만 반환한다. 응답에는 단계, 상태, 템플릿 버전, 6개 서류 슬롯의 업로드 상태, `uploadedCount`, 현재 체크리스트 답변, `confidence`, 분석 결과 요약을 포함한다. 다른 사용자 소유이거나 존재하지 않으면 모두 `404 ANALYSIS_CASE_NOT_FOUND`다.

### 문서 업로드와 삭제

문서 업로드는 `multipart/form-data`의 `documentType`, `file`을 받는다. 현재 단계에 없는 문서 종류, 빈 파일, 허용하지 않은 MIME 타입, 10MiB 초과 파일은 거절한다. 성공 시 생성 또는 교체된 문서 메타데이터와 새 진행률을 반환한다.

문서 삭제는 본인 케이스와 해당 케이스 소속 문서를 함께 확인한다. 존재하지 않거나 소유자가 다르면 `404 ANALYSIS_DOCUMENT_NOT_FOUND`다.

`ANALYZED` 케이스의 문서 업로드·교체·삭제는 `409 ANALYSIS_CASE_LOCKED`다.

### 체크리스트 저장

체크리스트 저장은 현재 답변 집합 전체를 받는다. 빈 배열, 일부 답변, 모든 답변을 허용한다. 저장 성공 시 답변과 새 `confidence`, `missingInputs`를 반환한다.

`ANALYZED` 케이스의 답변 변경은 `409 ANALYSIS_CASE_LOCKED`다.

### 위험 분석 실행

분석은 필수 입력 조건 없이 실행한다. 서버는 현재 주택 정보, 문서 업로드 여부와 체크리스트 답변을 읽고 하나의 트랜잭션에서 입력 스냅샷과 규칙 기반 결과를 저장한 뒤 케이스를 `ANALYZED`로 변경한다.

요청의 `Idempotency-Key`는 필수다. 같은 케이스와 같은 키의 재요청은 저장된 결과를 그대로 반환한다. 이미 분석된 케이스에 다른 키를 보내면 `409 ANALYSIS_ALREADY_COMPLETED`다.

입력 근거가 없으면 다음 의미의 결과를 반환한다.

```json
{
  "score": null,
  "grade": "UNKNOWN",
  "confidence": 0,
  "missingInputs": [
    "DOCUMENT:REGISTRY_CERTIFICATE",
    "CHECKLIST:LANDLORD_IDENTITY_CONFIRMED"
  ],
  "message": "분석할 정보가 부족합니다."
}
```

## 사용자 격리와 동시성

모든 케이스·문서 조회는 ID와 인증 사용자 ID를 함께 조건으로 사용한다. 다른 사용자 데이터의 존재 여부를 응답으로 구분하지 않는다.

분석 실행은 케이스 행을 잠그고 결과 존재 여부를 다시 확인한다. 데이터베이스의 케이스당 결과 유일 제약을 최종 기준으로 사용해 동시에 들어온 중복 분석이 두 결과를 만들지 못하게 한다.

## 오류 처리

- 잘못된 단계·문서 종류·문항·중복 문항은 `400`으로 반환한다.
- 빈 파일이나 허용하지 않은 형식은 `400 INVALID_DOCUMENT`로 반환한다.
- 파일 크기 초과는 `413 DOCUMENT_TOO_LARGE`로 반환한다.
- 본인 소유가 아닌 주택·케이스·문서는 존재하지 않는 것과 같은 `404`로 반환한다.
- 분석 후 입력 변경은 `409 ANALYSIS_CASE_LOCKED`로 반환한다.
- 다른 멱등성 키를 사용한 중복 분석은 `409 ANALYSIS_ALREADY_COMPLETED`로 반환한다.

## 테스트 전략

- 마이그레이션 테스트로 외래 키, 문서 슬롯 유일 제약, 케이스당 결과 유일 제약과 BLOB 크기 타입을 확인한다.
- 템플릿 테스트로 세 단계, 단계별 6개 서류 슬롯, 섹션·문항 순서와 안정적인 키를 검증한다.
- 서비스 테스트로 사용자 격리, 문서 교체·삭제, 체크리스트 전체 교체, 빈·부분 입력 허용, 분석 후 잠금을 검증한다.
- 규칙 엔진 테스트로 규칙 매칭, 점수 범위, 등급 경계, 누락값 비점수화, `UNKNOWN`, `confidence`, 규칙 버전을 검증한다.
- 동시성 테스트로 같은 케이스가 두 분석 결과를 만들 수 없음을 검증한다.
- MVC 테스트로 multipart 계약, 요청 검증, 상태 코드, 멱등성 키와 응답 구조를 검증한다.
- 관련 패키지 테스트, 전체 `./gradlew test`, `./gradlew bootJar`를 순서대로 실행한다.

## 완료 기준

- 사진의 세 단계, 단계별 서류 6종, 탭형 체크리스트와 부분 입력 흐름을 API로 지원한다.
- 아무 서류나 답변이 없어도 분석 요청이 성공하고 `UNKNOWN` 결과를 반환한다.
- 동일한 입력·규칙 버전은 항상 동일한 결과를 반환한다.
- 다른 사용자의 주택·케이스·문서에 접근할 수 없다.
- 분석 완료 후 입력이 고정되고 같은 멱등성 키에는 같은 결과가 반환된다.
- 관련 테스트, 전체 테스트와 실행 JAR 생성이 통과한다.
